## Reviewer notes

Three findings need a decision rather than a repair, and those are the ones to read
first.

**`R41-01` is the one that would survive into production.** The election design is
sound and the comment explaining it is right — one replica's insert wins and the rest
learn from the database rather than from a race they had to observe. What is
unresolved is where that insert commits. The class doc commits to sharing the caller's
transaction with the deletions, and under that contract a losing insert does not
receive a duplicate-key error at all; it waits on the winner's uncommitted unique-index
lock for the length of the winner's purge, then fails as 1205. The fix is a choice
between two coherent designs: claim in its own committed transaction and keep the
deletions in a second one, which makes the insert a real race and the lease the only
thing protecting the work; or keep one transaction and classify lock-wait timeout as a
refusal too, accepting that every loser blocks for `innodb_lock_wait_timeout` each
tick. The first is cleaner and matches how the lease is already described. Either way
the integration test has to claim from two open transactions, because the current one
cannot observe the failure mode.

**`R41-02` is a data-integrity defect that the code's own documentation predicts.**
`fail` explains exactly why counts are recorded on failure — an operator reading the
row needs to know three hundred rows went — and then `complete` overwrites that number
on the next attempt. The merge belongs in SQL so it holds under the claim predicate
rather than in a read-modify-write the lease could interleave.

**`R41-03` is cheap now and expensive in `P7-T04`.** Nothing consumes the refusal reason
yet, which is precisely why the contract should be corrected before a scheduler is
written against it. As it stands, `exhausted` is an edge-triggered signal and `taken` is
level-triggered, and the two are being read as if both were level-triggered.

`R41-05` deserves a note because it repeats a class this repo has already paid for.
`R39-02` was a bound that was asserted and never applied; `statementTimeoutMs` is the
same shape, and `assertRetentionBounds` is deriving the claim lease from it. The delete
path that will consume it arrives in `P7-T03`, so the bound having no consumer is not
itself wrong — but the reads this slice does ship are unbounded, and they are the ones
an operator will point at a production database with a backlog.
