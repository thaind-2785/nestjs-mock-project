## Reviewer notes

Three of the four High findings share one root: **the run reports success by default and
has to be told otherwise.** `complete()` is reached whenever no exception escaped the
batch loop, and three different "this did not really work" signals — a provider that
refused everything (`R42-03`), a budget that ran out (`R42-04`), and a claim that was
lost — are each represented only as a local variable or a discarded field. The ledger
row is the durable artifact this phase exists to produce, and right now it says
`SUCCEEDED` in all three cases. The fix is not three patches but one decision: what
`complete()` is allowed to be called with, and what the run must write when it is not
entitled to call it.

**`R42-01` is the one to reproduce before fixing.** The lease arithmetic is sound for the
two pure-SQL tasks and wrong for the two that call the object store, because
`assertRetentionBounds` reasons about statements and those tasks spend their time in
network calls the bound never sees. There are two coherent fixes and they are not
equivalent: check the deadline inside the provider loops (the batch becomes
interruptible, and partial batches become normal), or renew the lease as a batch
progresses (the batch stays atomic, and the run needs a heartbeat). The first is
smaller and fits the "a task never throws away work it has already done" contract the
tasks service already states. `R42-09` should be fixed with it — handing Phase 3's loop
a number tuned for rows-per-statement is what makes the batch long enough to matter.

**`R42-02` deserves a note because it is the third appearance of one pattern.**
`R39-02` was a drain bound asserted and never applied; `R41-05` was a statement bound
declared and never applied; this is the helper for that bound, written and never called.
Each time the configuration check passed and the property it described was absent. The
cheapest guard against a fourth is a test that asserts the _effect_ — the session
variable, the drain value, the elapsed bound — rather than the relationship between two
constants.

`R42-10` is the one item in this report that is genuinely the owner's. Removing
`--dry-run` as a requirement is defensible: the flag guarded a build that could not
delete, and this one can. What replaced it is nothing, and the command that deletes five
tables is now the zero-argument default. A required `--delete` costs one line and one
test, and keeps the property `P7-T02` established.

## Residual risk and follow-up

- `R42-01` and `R42-05` are argued from code and configured numbers, not reproduced.
  Both should be pinned by a test as part of the fix rather than accepted on reading.
- `R42-07` rests on the claim that `object_key` is unique per job. That follows from
  `stagingObjectKey` and `uq_export_jobs_outbox_event` today; if Phase 6 ever publishes a
  key that is not derived from the job id, the guard becomes necessary and the branch
  becomes wrong in the other direction. Either way the current pair — an N+1 guarding an
  impossible case with an incorrect handler — should not ship.
- This review authored no fixes, so no gate was run and the branch's own green status is
  the author's. After the four High findings are closed, `npm run verify` is owed once
  before handoff, per `AGENTS.md`.
- The review is not independent: the same agent family authored the change. A second
  reader should re-read `R42-01`, `R42-03` and `R42-04` before the verdict is cleared.
