## Author disposition, 2026-09-24

### The Blocker and the High findings that shared its cause

`R45-01`, `R45-03`, `R45-04`, `R45-06`, `R45-07` and `R45-14` were one defect in six
places, and the error log already had a name for it: a bound asserted where it is declared
rather than observed where it runs. This is its seventh and eighth appearance.

The deploy now asks three questions instead of one. Did the platform's own deployment
reach `SUCCESS`; is `/health/live` reporting the commit being deployed; do the
dependencies answer. Previously it asked only the third, and the third was answered by the
container about to be replaced — Railway keeps the outgoing revision serving until the new
one is healthy, so poll one returned `200` before anything had happened.

The worker is verified the same way, through the platform, because it has no HTTP surface
to ask. `rolledBack` is now the rollback's return value rather than an unconditional
`true`. `APP_IMAGE` is rejected unless it names a digest, and the workflow policy checks
the value exported rather than only the command that resolved it. The rollback restores
only what it actually wrote.

The fake was rewritten with them. It used to answer `200` immediately, which meant every
test agreed with a deploy that verified nothing; its liveness revision now changes only
when a deployment succeeds. Eleven mutations were run against the result and one failed to
fail — the test for `R45-14` had staged a rollback that died before reaching the worker,
so it could not observe the rule it was named for. Rewritten, then it failed.

### The second Blocker

`R45-02` was a documentation failure with a working system behind it: R2 in the spec, the
plan, the runbook's whole setup section and its environment block, against Filebase in
production. A reader following the runbook would have created the wrong account and set
`OBJECT_STORAGE_REGION=auto` where Filebase needs `us-east-1` — and the troubleshooting
table would have sent them the wrong way. Every mention now names Filebase, and the setup
step says why the bucket must be S3 object storage and not IPFS.

### Accepted, with reasons

- **`R45-08`** — nine acceptance criteria claimed without evidence. Six of them now have
  it: the first observed deploy ran on 2026-09-24 at `7d40edf`, and `PLAN-012` carries the
  log, the digests, the revision the public address reports, and the TLS and OpenAPI
  checks. The six demonstration flows were walked through Swagger by the owner the same
  day. The ninth — a live rollback drill — is accepted as a residual risk: the owner chose
  not to fail a live deployment on purpose, the path has fifteen unit cases and seven
  mutations against a fake that models how the platform actually behaves, and the manual
  recovery is a minute in the Railway dashboard.
- **`R45-09`** — closed on 2026-09-24 rather than accepted. The owner enabled branch
  protection; `gh api` now returns `Verify repository` as the required context with
  `strict` set. `ADR-0009` records the verification and the manifest reads `verified`. What
  was accepted was the gap between a claim and a check, and the fix was to run the check.

### Everything else

`R45-05` (a merge on `main` could cancel a deploy mid-flight), `R45-10` through `R45-13`,
and `R45-15` through `R45-32` are fixed. Four of them were the same shape as the Blocker in
a different file: the policy claimed workflow-wide action pinning and checked one job; the
deploy job's steps were unconstrained beyond one forbidden hostname; the migration command
was a second copy of a package script that nothing compared; and a fixture asserted a
status by re-reading the manifest it was written from.

`R45-17` was a decision rather than a defect, and the decision is to keep arm64 — the
rationale is now the honest one. The original said the deployment host was arm64, which
stopped being true when the platform changed; what keeps it is a developer on Apple silicon
pulling the image to reproduce a deployed failure.
