# SPEC-003: Platform foundation

- Status: Accepted
- Owner: Project owner
- Last updated: 2026-08-27
- Scope: Required
- Related endpoints / ADRs: `HEALTH-01`, `HEALTH-02`; no new ADR required at draft
  time

## Problem and outcome

Product modules cannot be implemented safely on the current minimal NestJS scaffold
until runtime configuration, persistence, localization, API conventions,
observability, dependency health, and local infrastructure have one tested baseline.

After this phase, a developer can start the API against documented local dependencies,
run TypeORM migrations explicitly, inspect the API contract, receive localized and
request-correlated errors, and use liveness/readiness endpoints in later CI/CD gates.
The foundation must be reusable by the auth, rooms, bookings, files, notifications,
reports, and scheduling phases without implementing those business capabilities yet.

## In scope / out of scope

### In scope

- Focused, fail-fast validation for application, MySQL, Redis, object-storage,
  localization, logging, and health configuration.
- A committed `.env.example` containing names and safe example values only.
- NestJS bootstrap conventions: `/api/v1` global prefix, global DTO validation,
  standard error contract, request correlation, and graceful shutdown.
- English and Vietnamese localization with English as the deterministic fallback.
- OpenAPI/Swagger generation from the running application in enabled environments.
- Structured application logs and one server-generated request ID per HTTP request.
- MySQL 8 connectivity through TypeORM with `synchronize: false`, an explicit
  migration CLI path, and a reversible integration-test fixture proving the
  mechanism without adding a fake production table.
- Redis and S3-compatible object-storage connectivity required by readiness.
- Public liveness and readiness endpoints that reveal no credentials or internal
  connection details.
- Docker Compose dependency services for MySQL, Redis, MinIO, and Mailpit with
  healthchecks, named volumes, and documented local commands.
- Reusable integration/E2E setup that fails with an actionable prerequisite when
  required Compose services are unavailable; required tests must never silently skip.

### Out of scope

- Google OAuth, JWT, refresh sessions, user/RBAC behavior, and first-admin tooling.
- Product tables and migrations for users, rooms, bookings, attachments, outbox,
  exports, or scheduling. They remain in their owning vertical slices.
- BullMQ queues, Gmail delivery, Worker Threads, and scheduled jobs.
- Room file-upload endpoints or a production cloud-provider selection.
- Production Docker image hardening, container publishing, deployment, branch
  protection, and rollback automation; those belong to the CI/CD phase.
- Starting the future `worker` service in Phase 1. The final Compose topology will add
  `api`/`worker` services when their runtime/image contract exists.

## User-visible contract

All paths below use the `/api/v1` base path.

### `GET /health/live`

- Public and unauthenticated for process/orchestrator probes.
- Does not call MySQL, Redis, object storage, Mailpit, or external providers.
- Returns HTTP `200` while the NestJS HTTP process can serve requests.
- Response includes `status: "ok"` and the current `requestId`; it does not expose
  hostnames, credentials, stack traces, versions, or environment values.

### `GET /health/ready`

- Public and unauthenticated for deployment probes.
- Checks MySQL, Redis, and S3-compatible object storage with bounded timeouts.
- Returns HTTP `200` and `status: "ok"` only when all required dependencies pass.
- Returns HTTP `503` and stable error code `SERVICE_NOT_READY` when any required
  dependency fails or times out.
- Failure details may identify the dependency class (`mysql`, `redis`, `storage`) but
  never include credentials, bucket secrets, raw driver errors, or network addresses.
- Mailpit/Gmail is not an API-readiness dependency because later email delivery is
  asynchronous through an outbox/queue.

### Cross-cutting HTTP behavior

- Every response includes an `X-Request-Id` generated by the server as a UUID.
- Errors use `{ statusCode, code, message, details?, requestId }`.
- Request DTOs reject unknown properties and apply transformation only where the DTO
  explicitly declares it.
- `Accept-Language` selects `en` or `vi`; missing/unsupported languages fall back to
  English. Stable error `code` values are never localized.
- Swagger is served at `/api/docs` only when explicitly enabled by validated config;
  it defaults to enabled locally/test and disabled in production.

## Business rules and state transitions

This phase introduces no hotel-domain state transition.

Foundation lifecycle rules:

1. Invalid or missing required configuration stops startup with field names and safe
   validation messages, never secret values.
2. Application startup never runs schema migrations implicitly.
3. Liveness is independent of downstream health; readiness fails closed on a required
   dependency failure.
4. A request has exactly one server-generated correlation ID reused by response,
   standard error body, and structured request-completion log.
5. Localization changes human-readable messages only; clients branch on stable codes.

## Data and migration impact

- Add TypeORM configuration for MySQL 8 with migrations as the schema source of truth
  and `synchronize: false` in every environment.
- Add a reversible migration fixture used only by integration tests. Do not add a
  production marker table or no-op migration solely to prove the toolchain.
- Migration commands use the same validated database configuration as the app but run
  as an explicit process suitable for local use and a later deployment job.
- Integration tests prove fixture migration up/down from an empty disposable database
  and the documented production rollback/forward-fix policy.
- The users/auth schema begins in the Auth and RBAC phase so its migration, service,
  and tests remain one vertical change.

## External services, async work, and failure behavior

- Local dependencies are MySQL, Redis, MinIO, and Mailpit. Compose pins reviewed image
  versions, uses healthchecks and named volumes, and keeps credentials in environment
  configuration rather than images or committed secrets.
- Readiness checks are concurrent or otherwise bounded so one dependency cannot hang
  the endpoint indefinitely. Overall and per-dependency timeouts are configurable with
  safe bounds.
- Failure to reach a dependency produces a `503` readiness result and a sanitized log;
  it must not crash an otherwise live process.
- Redis is prepared for later BullMQ/session use, MinIO for later file/export use, and
  Mailpit for later email tests; no queue, upload, or email is performed in this phase.

## Security, privacy, and abuse cases

- No credential, token, cookie, full connection string, provider payload, or raw
  environment value may appear in logs, HTTP responses, Swagger examples, test
  snapshots, or committed documentation.
- `.env` and other local secret files remain ignored; `.env.example` contains no real
  secrets.
- Health endpoints expose only coarse dependency state and use short timeouts. Add a
  lightweight rate limit later through the shared abuse-control slice if health-probe
  traffic becomes externally exposed; Phase 1 must keep checks cheap and bounded.
- Request IDs are generated server-side rather than trusting arbitrary client input.
- Global validation uses whitelist plus rejection of unknown request fields.
- CORS is deny-by-default until exact frontend origins and the OAuth handoff are
  selected before Phase 2.

## Observability and operations

- Structured request logs include timestamp, level, request ID, method, normalized
  route, response status, and duration. They exclude request/response bodies by
  default.
- Startup logs record enabled non-secret capabilities and fail before listening when
  configuration is invalid.
- Readiness dependency failures use stable internal failure classes and sanitized
  messages suitable for CI/deployment diagnosis.
- Graceful shutdown stops accepting traffic and closes initialized MySQL/Redis/storage
  clients within a bounded period.
- Local documentation provides start, stop, health, migration, and test-prerequisite
  commands without depending on sibling repositories or undocumented machine state.

## Acceptance criteria

- [ ] Given a required configuration value is missing or invalid, when the API starts,
      then startup fails before listening and reports the field without its value.
- [ ] Given a valid local configuration, when the API starts, then all routes use the
      `/api/v1` prefix and Swagger is available only according to its config flag.
- [ ] Given English, Vietnamese, missing, and unsupported language headers, when a
      localized validation/error response is returned, then `en`/`vi` behave as
      configured, fallback is English, and the stable error code does not change.
- [ ] Given any HTTP request, when a response or error completes, then one
      server-generated request ID is present consistently in the header, error body
      where applicable, and structured completion log.
- [ ] Given the process is serving, when `/api/v1/health/live` is requested, then it
      returns `200` without contacting downstream dependencies.
- [ ] Given MySQL, Redis, and MinIO are healthy, when `/api/v1/health/ready` is
      requested, then it returns `200` within the configured timeout.
- [ ] Given any required readiness dependency is unavailable or slow, when readiness
      is requested, then it returns `503 SERVICE_NOT_READY` without leaking connection
      details while liveness remains `200`.
- [ ] Given an empty disposable MySQL database, when the migration integration suite
      runs, then the reversible fixture migrates up/down with `synchronize: false`;
      no fake production schema object is introduced.
- [ ] Given a clean machine with Docker Compose and the documented environment, when
      dependency services start, then MySQL, Redis, MinIO, and Mailpit become healthy
      without any real external provider call.
- [ ] Given Compose prerequisites are absent, when an integration/E2E suite requiring
      them runs, then it fails with an actionable message rather than silently
      skipping.
- [ ] Given the final Phase 1 implementation, when `npm run verify` runs from a clean
      checkout with documented prerequisites, then Harness checks, formatting, lint,
      unit, integration, E2E, and build all pass.
- [ ] An independent reviewer finds no unresolved Blocker/High issue, and accepted
      Medium/Low findings have a recorded disposition.

## Test strategy

- Unit: configuration schemas and boundary values; locale selection/fallback; error
  mapping; request-ID generation; readiness aggregation and timeout mapping.
- Integration: Nest module graph; real MySQL connection and migration up/down path;
  real Redis ping; real MinIO bucket/readiness operation; shutdown cleanup.
- E2E: global prefix, validation/error body, localized messages, request ID,
  liveness/readiness `200` and readiness `503` paths, conditional Swagger exposure.
- Compose smoke: dependency healthchecks and persistent-volume behavior without real
  Google, Gmail, cloud, or payment calls.
- Full handoff: `npm run verify` once before independent review and once more only if
  accepted Blocker/High fixes change gate inputs.

## Assumptions and open questions

### Assumptions accepted for this draft

- English is the fallback locale; clients request Vietnamese with
  `Accept-Language: vi`.
- Swagger uses `/api/docs` and is disabled by default in production.
- API readiness requires MySQL, Redis, and object storage, but not mail transport.
- Phase 1 Compose starts dependency services only. Full `api`/`worker` Compose topology
  is completed when the worker and production image contracts exist.
- Phase 1 proves migration infrastructure without creating product-domain tables.
- Exact dependency/image versions are selected and locked in the implementation plan
  after checking compatibility with Node 22 and NestJS 11.

### Decisions intentionally deferred

- Exact frontend origin and OAuth callback/handoff mechanism: before Phase 2.
- Production object-storage vendor, bucket policy, and file limits: before Phase 3.
- Gmail transport and sender identity: before Phase 5.
- Deployment provider, secret store, migration runner, and rollback method: before
  Phase 8.

No owner decision currently blocks planning Phase 1. Any assumption above may be
changed during owner review before this spec is accepted.

## Rollout and rollback

- Roll out locally first with Compose dependency health and migration tests, then add
  the foundation to the existing repository verification gate.
- Configuration and bootstrap changes are reverted together if startup compatibility
  fails; no fallback may enable `synchronize`.
- Migration rollback is exercised only against disposable/local test data. Once a
  migration reaches a shared environment, prefer an explicit compatible down migration
  or forward fix according to the reviewed plan rather than destructive ad hoc SQL.
- Stopping Compose preserves named volumes by default. Volume deletion is a separate,
  explicit destructive developer action and is never part of normal verification.
